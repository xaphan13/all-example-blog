# FastAPI + Jinja2 + Tailwind — демо-проект

Минимальное, но «правильно собранное» веб-приложение на FastAPI с серверным
рендерингом на Jinja2 и стилями Tailwind CSS. Проект написан как
**демонстрация для статьи**: цель — не богатый функционал, а понятная и
масштабируемая архитектура, на которую можно опереться в реальном приложении.

---

## Быстрый старт

```bash
# виртуальное окружение уже создано в ./venv
source venv/bin/activate
pip install -r requirements.txt

python3 main.py          # → http://127.0.0.1:8000
```

Документация API (Swagger) доступна на `http://127.0.0.1:8000/docs`.

## Структура проекта

```
NPMPythonDemoProject/
├── main.py              # точка входа: фабрика приложения + запуск uvicorn
├── router.py            # агрегатор: собирает все под-роутеры в один объект
├── requirements.txt
├── core/                # инфраструктура приложения
│   ├── config.py        # настройки (pydantic-settings)
│   └── templating.py    # единый экземпляр Jinja2Templates
├── routers/             # маршруты, разбитые по смыслу
│   ├── pages.py         # HTML-страницы (/, /about)
│   └── api.py           # JSON API (/api/...)
├── static/              # отдаётся как есть по /static/...
│   ├── css/style.css    # свой CSS поверх Tailwind
│   └── js/main.js       # клиентская логика
└── templates/           # шаблоны Jinja2
    ├── base.html        # базовый layout (Tailwind подключается здесь)
    ├── partials/        # переиспользуемые куски (navbar, footer)
    └── pages/           # контент конкретных страниц
```

## Архитектурные решения и почему именно так

### 1. Фабрика приложения `create_app()`

В [main.py](main.py) приложение собирается внутри функции `create_app()`, а не
создаётся как глобальный объект «по ходу файла».

**Почему:** фабрика изолирует сборку приложения. Это упрощает тестирование
(можно создать отдельный экземпляр с другими настройками), исключает
side-эффекты на импорте и оставляет чёткую границу «вот здесь приложение
собирается целиком». Запуск через `uvicorn.run("main:app", ...)` под
`if __name__ == "__main__"` позволяет стартовать одной командой
`python3 main.py` и при этом сохраняет работающий `--reload`.

### 2. `router.py` — единая точка подключения роутеров

`main.py` ничего не знает о конкретных страницах: он подключает один объект
`router` из [router.py](router.py), а тот уже включает в себя под-роутеры из
пакета `routers/`.

**Почему:** добавление нового раздела сводится к двум шагам — создать модуль в
`routers/` и дописать одну строку `include_router`. `main.py` при этом остаётся
неизменным. Это и есть защита от «простыни»: маршруты не накапливаются в одном
файле, а растут вширь по смысловым модулям.

### 3. Разделение `pages` и `api`

Страницы ([routers/pages.py](routers/pages.py)) и JSON-эндпоинты
([routers/api.py](routers/api.py)) живут в разных роутерах. API вынесен под
префикс `/api` и помечен своим тегом.

**Почему:** у HTML и REST разные форматы ответа, разные потребители и разная
эволюция. Разделение делает явной границу между «отдаём страницы» и «отдаём
данные», а теги аккуратно группируют эндпоинты в `/docs`.

### 4. Слой `core/` — инфраструктура отдельно от маршрутов

В `core/` лежит то, что не относится к конкретным эндпоинтам:
конфигурация и настройка шаблонизатора.

- [core/config.py](core/config.py) — класс `Settings` на pydantic-settings.
  Все параметры (хост, порт, пути, debug) читаются из окружения/`.env` с
  валидацией типов. Единый экземпляр `settings` — одна точка правды по
  конфигу, никаких «магических» констант, разбросанных по коду.
- [core/templating.py](core/templating.py) — один экземпляр `Jinja2Templates`.
  Глобальные переменные шаблонов (например, `app_name`) и в будущем фильтры
  задаются в одном месте, а роутеры просто импортируют готовый `templates`.

**Почему:** инфраструктурный код имеет свойство расползаться по обработчикам.
Вынос его в `core/` оставляет роутеры тонкими и сфокусированными на логике
конкретных маршрутов.

### 5. Шаблоны через наследование и партиалы

[templates/base.html](templates/base.html) задаёт общий layout, страницы в
`templates/pages/` наследуют его через `{% extends %}` и заполняют только блок
`content`. Повторяющиеся части (навбар, футер) вынесены в `partials/` и
подключаются через `{% include %}`.

**Почему:** ни один шаблон не дублирует `<head>`, подключение стилей или
структуру страницы. Меняется layout — правится один файл. Это прямой аналог
принципа DRY на уровне разметки.

### 6. Tailwind через CDN, а не через npm-сборку

Tailwind подключается тегом `<script src="https://cdn.tailwindcss.com">` прямо
в `base.html`.

**Почему:** это демо-проект, и цель — показать архитектуру backend'а, а не
настройку фронтенд-сборки. CDN убирает из проекта `package.json`,
`node_modules` и шаг компиляции CSS — запустить можно сразу. В продакшене
Tailwind ставят через CLI/PostCSS с очисткой неиспользуемых классов, но для
статьи такой оверхед только отвлекал бы. Папка `static/css/` при этом остаётся
для собственных стилей поверх Tailwind.

### 7. Современная сигнатура `TemplateResponse`

Шаблоны рендерятся как `templates.TemplateResponse(request, "name.html", {...})`
— с `request` первым аргументом.

**Почему:** это актуальный API Starlette/FastAPI. Старая форма
(`TemplateResponse("name.html", {"request": request, ...})`) помечена как
устаревшая, поэтому используем новую, чтобы код не выдавал deprecation-warning
и оставался валидным на свежих версиях.

## Как расширять

- **Новая страница:** добавить обработчик в `routers/pages.py` и шаблон в
  `templates/pages/`.
- **Новый раздел API:** создать модуль в `routers/`, подключить его одной
  строкой в `router.py`.
- **Бизнес-логика:** по мере роста выносить из обработчиков в отдельный слой
  `services/`, оставляя роутеры тонкими.
- **Новый параметр конфигурации:** добавить поле в `Settings` — оно сразу
  читается из окружения/`.env`.
