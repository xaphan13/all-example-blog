# Оценка качества кодовой базы

## Общая оценка

Кодовая база — компактная, хорошо читаемая и последовательная для проекта небольшого размера. Автор сознательно избегает избыточной инфраструктуры (ORM, frontend-фреймворки, CMS), что снижает когнитивную нагрузку. Стиль близок к современному Python: type hints, f-strings, pathlib, `async` lifespan.

Однако отсутствие тестов, CI/CD, линтеров и форматёров заметно снижает зрелость проекта с точки зрения промышленной разработки.

## Соответствие стандартам

### SOLID

- **SRP (Single Responsibility)**:
  - Хорошо: `app/queries/*` отвечают только за SQL; `../app/markdown_render.py` только за рендеринг.
  - Плохо: роутеры `admin.py` и `public.py` смешивают HTTP-обработку, валидацию, бизнес-логику и рендеринг. Например, `_save_tags` в `admin.py` — это доменная операция, а не ответственность роутера.
- **OCP (Open/Closed)**: расширение функциональности требует прямого изменения роутеров и шаблонов.
- **LSP**: не применимо (нет иерархий классов).
- **ISP**: не применимо напрямую; зависимости через `Depends(get_db)` изолируют слой БД.
- **DIP**: `get_db` инжектируется в endpoint, но модули `queries` напрямую принимают `db`-соединение, что упрощает тестирование.

### DRY

- Повторяющиеся операции (рендеринг markdown, сохранение тегов, генерация slug) вынесены в отдельные функции.
- SQL-колонки постов вынесены в `_COLUMNS` (`../app/queries/posts.py`).
- Параметризация `published_at` через `CASE WHEN` повторяется в `posts.create`, `posts.update`, `posts.set_published` — это допустимо, но можно было бы централизовать.

### KISS

- Архитектура проста и понятна. Нет лишних абстракций.
- Использование raw SQL вместо ORM оправдано для небольшого проекта.

### Идиомы языка

- Используются `pathlib.Path`, `str | None` (Python 3.10+ union types), `asynccontextmanager`.
- Корректная работа с `psycopg.rows.dict_row` для получения результатов в виде словарей.
- Комментарии в коде преимущественно на испанском — это не влияет на работу, но для международной команды стоит перевести на английский.

## Технический долг и code smells

### Высокий приоритет

1. **Отсутствие тестов**. Нет unit-, integration- и E2E-тестов. Любое изменение в рендеринге markdown, SQL или авторизации не верифицируется автоматически.
2. **Отсутствие CI/CD**. Нет GitHub Actions / GitLab CI для линтинга, тестов и сборки образа.
3. **CSRF-уязвимость**. Все POST-формы админки (`login`, `logout`, `create/edit/publish/delete`, `cleanup`) не защищены CSRF-токенами. Хотя cookie `SameSite=Lax` снижает риск, это не полноценная защита.
4. **Нет ограничения размера загружаемых файлов**. `POST /admin/api/images` позволяет залить файл произвольного размера.
5. **Загрузка файлов без проверки MIME-типа и содержимого**. Проверяется только расширение; возможно переименование опасных файлов.
6. **Нет валидации входных данных форм**. `title`, `slug`, `summary` и др. принимаются как `str = Form()` без `min_length`/`max_length` и без защиты от XSS в пользовательских полях (хотя автор единственный пользователь).
7. **Жёстко зашитый URL старого сайта** в `../scripts/migrate_old_posts.py`: `Path.home() / "Documents" / "wwwdiegolonio"`. Это не конфигурируется.

### Средний приоритет

8. **Роутеры разрослись**. `../app/routers/admin.py` (225 строк) содержит endpoint-функции, схемы Pydantic (`PreviewIn`), вспомогательные функции (`_save_tags`) и бизнес-логику. Стоит выделить сервисный слой.
9. **Прямая генерация XML в коде** (`sitemap.xml`). Работает, но менее безопасна, чем шаблон с экранированием.
10. **Отсутствие пагинации в `/search` и `/tags/{slug}`**. При большом количестве постов страницы станут тяжёлыми.
11. **Нет механизма retry / backoff для подключения к БД**. В продакшене compose ждёт `service_healthy`, но в dev-окружении `pool.open()` может упасть, если Postgres ещё не готов.
12. **Отсутствие healthcheck endpoint**. Нет `/health` или `/ready` для мониторинга и оркестратора.
13. **Магические числа**: `POSTS_PER_PAGE = 6`, `SESSION_MAX_AGE`, `MIN_AGE_SECONDS` вынесены в константы — это хорошо, но они разбросаны по модулям.

### Низкий приоритет

14. **Нет документации API**. Хотя приложение SSR, админ API (`/admin/api/*`) мог бы иметь схему.
15. **Нет логирования бизнес-событий**: создание/удаление постов, вход/выход администратора не логируются.
16. **Нет graceful degradation**: если CDN KaTeX недоступен, формулы не отобразятся.

## Безопасность и надёжность

| Аспект | Оценка | Примечание |
|--------|--------|------------|
| Хранение паролей | ✅ Хорошо | argon2-cffi |
| Подпись cookie | ✅ Хорошо | itsdangerous URLSafeTimedSerializer |
| Cookie-флаги | ⚠️ Средне | HttpOnly, SameSite=Lax, но нет `Secure` в dev; в prod за TLS отвечает Cloudflare |
| CSRF | ❌ Слабо | Нет токенов в формах |
| XSS | ⚠️ Средне | `| safe` для `content_html` оправдан (только админ), но поля title/summary/slug не экранируются явно — Jinja2 делает это по умолчанию |
| Загрузка файлов | ❌ Слабо | Нет ограничения размера, проверки MIME, sandbox |
| SQL-инъекции | ✅ Хорошо | Везде параметризованные запросы `%s` |
| Зависимости | ✅ Хорошо | `../uv.lock` фиксирует версии |
| Секреты | ✅ Хорошо | Через `.env` / переменные окружения; примеры не содержат реальных ключей |

## Узкие места производительности

1. **`/sitemap.xml`** всегда выбирает до 1000 постов и строит XML в Python. При тысячах постов стоит кэшировать или пагинировать.
2. **`app/media_cleanup.py::delete_orphans`** собирает весь контент всех постов в одну строку в памяти. При большом количестве постов это не масштабируется.
3. **Full-text search** не ограничивает длину запроса; сложный запрос может быть медленным.
4. **Пул соединений** `max_size=10` подходит для низкой нагрузки, но не масштабируется горизонтально.
5. **Отсутствие CDN** для статики и медиа: все запросы идут через uvicorn.
